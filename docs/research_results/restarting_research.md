SECTION 1. PURPOSE OF THIS RESTART DOCUMENT

This document exists to restart the research on a stronger basis than the first cycle, not merely to continue it. The difference matters. A continuation mindset tries to preserve momentum. A restart mindset tries to preserve truth.

The project accumulated multiple layers over time:
- initial conceptual framing
- later deeper research passes
- a real but archived first-pass implementation
- a stronger active-root governance constitution
- a set of unresolved methodological questions that could easily be buried under engineering breadth

The project is therefore not being restarted because nothing exists. It is being restarted because too much exists, and not all of it deserves equal authority.

This document is meant to do five things at once:
- reconstruct the project accurately from repository evidence and the local HTML history
- separate stable ideas from drift, overreach, or false sophistication
- map the broader state of the art without collapsing too early into a single “winner”
- expose the implementation and benchmarking space as broadly as possible
- create a theory-heavy foundation for a new implementation cycle that is harder to fool and easier to defend academically

The goal is not elegance.
The goal is not preservation of every good-sounding branch.
The goal is not to select a final model family today.
The goal is to make the research space explicit enough that the next implementation cycle can proceed without quiet scope drift, benchmark drift, or feature inflation.


SECTION 2. GOVERNANCE BASIS AND EPISTEMIC RULES FOR THE RESTART

The active root has a much stronger governance philosophy than the legacy project did. That matters because the restart is now constrained not just by theory, but by a constitutional rulebook about how theory, design, code, tests, and updates must relate.

Established from repository evidence:
- AgentRules.md defines the mandatory dependency chain as Theory -> Design -> Code -> Tests and Benchmarks -> Update and Retraining Operations
- AgentRules.md forbids changing theory to justify code, changing design because code drifted, redefining benchmark logic to rescue weak implementation, and using README as a hidden override layer
- AgentRules.md requires exact uncertainty language: Not evidenced in repository materials. Plausible but unverified. Uncertain, verify manually.
- the governance layer treats benchmark integrity, explicit approval gates, contradiction visibility, evidence-gated completion, and operational continuity as first-class repository concerns

Supported by repository evidence:
- AgentAppendices.md makes the distributed governance architecture explicit and auditable rather than informal
- AgentCompliance.md and scripts/validate_agent_governance.py turn some governance expectations into mechanical checks
- AgentGlossary.md defines benchmark comparability change, stale-risk, approval gate, and immutable task contract in operational terms rather than loose language
- AgentMemory.md turns session continuity and operational truth into an auditable subsystem

The most important epistemic consequences for the restart are these.

First, theory is above code.

This means the scientific question must govern the architecture, not the other way around. If the codebase already supports an interesting branch, that does not make the branch scientifically central. This is the exact protection this project now needs, because the legacy snapshot is broad enough to tempt “implemented equals important” reasoning.

Second, uncertainty must remain explicit.

If a provider behavior is unclear, or if a capability is described in a doc but not evidenced in implementation or artifacts, the restart must not smooth that over. It must label it correctly. This matters particularly for live provider behavior, historical news coverage, split-source availability, and benchmark comparability between older and newer alignment policies.

Third, contradictions must be surfaced, not blended away.

This is especially important because this project has both archived theory documents and a newer governance shell. The documents do not always speak with one voice. A key example is that RESEARCH_DESIGN_old.md uses older embargo-style thinking in some news-alignment examples, while the current evaluation protocol defines an as-of-close same-day information set. That is a real contradiction in methodology framing, not a wording issue.

Fourth, benchmark comparability is a scientific object, not a reporting footnote.

The governance system explicitly uses terms like fully comparable, partially comparable, not comparable, and invalidated. That is unusually strong and exactly right for finance ML, where many false wins come from hidden changes to targets, universes, split logic, or feature construction.

Fifth, active-root governance is philosophically strong but operationally incomplete.

Established from repository evidence:
- validate_agent_governance.py requires docs/agent/agent_log/Current_State.md and docs/agent/agent_log/Event_Ledger.ndjson
- those files are currently missing in the active root
- running the validator fails for exactly that reason

This does not weaken the governance philosophy. It means the active root is stronger as a constitution than as a fully operating continuity system. For this restart investigation, the governance layer is therefore authoritative for behavior, but the archived snapshot remains authoritative for most implementation reality.

SECTION 4. RECONSTRUCTION OF THE PROJECT’S ORIGINAL INTENT AND EVOLUTION

The project began as a large, ambitious financial-news forecasting idea, but its framing improved over time.

Original intent.

The local HTML evidence and the older research design show that the project started from a desire to model stock reaction to financial news under a structured machine-learning pipeline. Early framing still carried traces of generic “news impact prediction” language, but even fairly early the project already rejected direct price prediction and leaned toward end-of-day, multi-horizon forecasting with recent news plus market features.

What remained stable.

Across HTML, RESEARCH_DESIGN_old.md, and the later archived docs, several elements stayed stable:
- end-of-day only
- market plus news multimodality
- multi-horizon forecasting
- event-state or event-driven language
- return-like targets rather than price levels
- strong leakage awareness
- strong emphasis on benchmarking and baselines

What expanded.

Over time the project expanded from theory into implementation reality:
- provider clients and raw payload preservation
- explicit data contracts
- split-event logic and adjusted-price generation
- event-state aggregation modules
- market-only baselines and a first multimodal model
- evaluation tooling, ablations, smoke runs, and broad tests

The project also expanded conceptually into many possible future directions:
- abnormal or factor-neutral targets
- ranking-first formulations
- uncertainty-aware outputs
- company knowledge-base and profile branches
- macro or regime context
- options signals
- graph-aware methods
- MoE ideas

What drifted.

The main drift was not the emergence of bad ideas in isolation. The main drift was loss of narrowness. Earlier reports sometimes moved from “map the space” toward “run a tournament and pick a winner”, even though later prompts and the current restart requirement clearly prefer understanding before final selection.

Established from repository evidence and HTML reconstruction:
- some prior deep-research documents explicitly performed scenario tournaments and final scenario selection
- the current restart requirement explicitly says not to choose the final architecture yet

That means part of the restart is methodological: avoid the previous tendency to collapse the space too early.

Conceptual maturation.

The strongest maturation step was the move from “individual article effects” toward “event state”. This is the single most important conceptual improvement in the project’s history. It transforms the project from a weak sentiment-prediction idea into a more defensible temporal information-state forecasting idea.

Another major maturation step was the explicit recognition that split handling is a scientific blocker. Once the project discovered that raw provider OHLCV could be unadjusted around known splits, it stopped treating corporate actions as a cosmetic issue and correctly treated them as part of label validity.

Methodological contradiction that must be preserved.

Older legacy theory documents include more conservative embargo-style examples for news alignment. The current evaluation protocol uses a same-day as-of-close information set. This should not be hidden. It means the project’s methodology evolved, and that older hypothetical benchmark targets or expectations are not automatically comparable with current evaluation logic.

What now looks central versus peripheral.

Central now:
- excess-return-oriented multi-horizon EOD forecasting
- event-state representation of recent aligned news
- split-safe labels
- market-only versus multimodal comparison
- benchmark and leakage discipline

Peripheral or later:
- static metadata enrichment
- uncertainty outputs
- derivative-family challenge tests
- relation-aware or graph-aware extensions
- dynamic profile branches


SECTION 5. CURRENT PROJECT IDENTITY

What the project is.

It is an end-of-day, leakage-aware, multi-horizon multimodal financial forecasting thesis project that tests whether recent aligned firm-news summarized as an event state adds predictive value beyond conservative market-only baselines for future stock performance expressed as excess or related return-style outcomes.

What the project is not.

It is not:
- a direct price-level prediction project
- an intraday or HFT system
- a trading-bot product thesis
- a pure NLP project divorced from market context
- a clean causal event-study project asserting isolated article-level impact
- a generic “use everything” multimodal finance platform

Strongest current academic framing.

The strongest academically defensible framing is:

Temporal multimodal forecasting of horizon-specific stock excess returns using conservative market features and a leakage-safe event-state representation of recent firm-related news.

Why this framing is strongest:
- it keeps the focus on forecasting rather than overstated causal claims
- it aligns with the repo’s architecture and evaluation logic
- it supports clean negative or conditional findings
- it directly encodes the main scientific comparison: market-only versus market plus event-state


SECTION 6. CORE THEORETICAL CONCEPTS

Event state
- Definition: a temporally aggregated representation of the recent information environment for a firm, constructed from aligned company-related news available by a defined cutoff.
- Why it matters: it is the project’s main theoretical differentiator and avoids the weakness of isolated article sentiment.

Multimodality
- Definition: joint use of heterogeneous information sources, here especially market history and text-derived event-state information, with optional static firm context.
- Why it matters: the project is not “text versus market”; it is whether text-derived state complements market context.

Multi-horizon forecasting
- Definition: forecasting different future horizons such as 1d, 5d, 20d, and optionally 60d, each potentially reflecting different mechanisms of reaction and repricing.
- Why it matters: immediate reaction and delayed information absorption are not the same problem.

Market-only baseline
- Definition: a model family trained only on conservative market features under the same data, splits, and evaluation policy as multimodal variants.
- Why it matters: it is the scientific reference class against which multimodal claims must be judged.

Company, profile, or context information
- Definition: static or slow-moving information about firms, such as sector, industry, identity, exchange, SIC, or more ambitious time-varying profile descriptions.
- Why it matters: potentially useful for generalization and entity structure, but secondary to the core market plus event-state question.

Regression versus ranking versus risk prediction
- Regression: predict numeric future outcome values.
- Ranking: predict relative ordering across stocks.
- Risk prediction: predict downside or uncertainty characteristics.
- Why it matters: these are different scientific tasks, not interchangeable metric views.

Temporal alignment
- Definition: all features for date t must be available by the official information cutoff for t.
- Why it matters: without it, the task is undefined and leakage claims are meaningless.

Leakage
- Definition: any use of future information, post-cutoff information, overlap contamination, revision-contaminated information, or holdout-fitted transformations that biases training or evaluation.
- Why it matters: in finance ML, weak true signal makes leakage disproportionately dangerous.

Benchmark comparability
- Definition: the condition under which old and new results belong to the same experimental family and can be interpreted as fair comparisons.
- Why it matters: without it, every improvement claim becomes ambiguous.

Modularity
- Definition: the ability to change one branch or family without silently altering upstream semantics or downstream evaluation meaning.
- Why it matters: this project’s main empirical value depends on clean ablations.

Thesis contribution versus engineering expansion
- Thesis contribution: the strongest defensible knowledge claim or benchmark-clean methodological result that survives the full protocol.
- Engineering expansion: the addition of more code, more files, more branches, or more modalities.
- Why it matters: the project must not confuse the second with the first.

Raw data stage
- fetch raw market OHLCV by ticker and date range
- fetch raw company-news payloads by ticker and date chunks
- fetch company KB data from SEC where needed
- fetch or normalize split events through preferred provider or fallback logic

- normalize provider-specific payloads into canonical interim tables

- annotate articles with as-of trade dates

Feature and label stage

- precompute article embeddings offline
- aggregate event states over fixed lookback windows with fixed decay rules
- generate multi-horizon labels from adjusted price histories and benchmark forward returns

Final modeling panel stage
- join adjusted prices, conservative market features, labels, optional event states, and optional company features

Split and evaluation stage
- create deterministic walk-forward folds
- purge overlapping label windows by maximum horizon
- optionally embargo dates around holdout blocks
- train market-only baselines first
- train first multimodal model second
- save checkpoints, predictions, and metrics per split
- evaluate stored predictions against frozen labels
- aggregate ablation summaries

SECTION 9. DATA PROCESSING AND DATA CONTROL

9.1 Data processing logic that should govern the project

The correct processing logic is not just “collect data and train.” It should follow explicit control rules:
- raw payloads remain immutable
- canonical interim tables are deterministic and provider-normalized
- adjusted prices are separate from raw prices
- all features are derived only from canonical validated upstream tables
- all final panels are versioned and manifest-backed
- all evaluation is performed against frozen panels and saved predictions

9.2 Split handling

Split handling is a primary scientific control, not a low-level engineering nuisance. The project must think of corporate actions as label correctness infrastructure. If adjusted prices are wrong, target validity is wrong. If target validity is wrong, every later comparison is weakened.

Supported by repository evidence:
- corporate_actions.py computes cumulative future split factors and applies backward adjustment to OHLC and forward scaling to volume
- split_events_pipeline.py implements provider-order logic and writes canonical split-event artifacts plus quality reports

Uncertain, verify manually.
- exact split-event completeness and behavior on the active real provider plan
Verification step: run known-split ticker checks over AAPL, TSLA, NVDA or similar and inspect whether mechanical split-day return spikes remain after adjustment.

9.3 Timestamp alignment

The project should think about text timing with the same seriousness it gives to price adjustment.

Correct rule under current repo policy:
- only articles available by market close on day t may enter day t features
- after-hours articles belong to the next valid trading day
- non-trading-day articles also roll forward
- timezone normalization must happen before date assignment

This rule is stronger than vague “use recent news” language and should remain the official alignment basis unless the benchmark family is intentionally redefined.

Deterministic deduplication should remain part of the canonical interim pipeline.

Best current rule:
- dedupe by URL first
- use hash fallback on normalized text and core metadata
- preserve source metadata for later conflict or dispersion features

This matters because news duplication can inflate density and create false attention signal.

SECTION 10. BLIND SPOTS, FAILURE MODES, AND CRITICAL RISKS

10.1 Leakage channels
- post-close or weekend news assigned too early
- overlapping multi-horizon label windows contaminating training
- feature scaling or imputation fit on non-train data
- company profile or metadata carrying future knowledge backward
- same-date cross-sectional leakage in ranking or normalization logic
- backfilled or revised external series treated as point-in-time true

10.2 Corporate actions contamination
- unadjusted splits create false extreme returns
- false returns contaminate labels and any downstream regression or ranking metric
- derivative-like transforms on raw prices amplify this problem even further

10.3 Benchmark invalidation triggers
- target family changes
- benchmark series changes
- split-source changes
- alignment-policy changes
- text-variant changes
- no-news handling changes
- universe changes
- fold construction changes
- missing-data filtering changes

10.4 Regime dependence
- a model can look good only in a bull market, only in high-volatility periods, or only in news-heavy regimes
- without year-by-year or regime-aware evaluation, the project can overstate stability

10.5 Survivorship issues
- using a current large-cap or current S&P 500 snapshot historically can exclude firms that disappeared, merged, or were removed
- this may bias learnability upward and must be acknowledged unless historical membership is reconstructed

10.6 Text timing errors
- timezone misparsing
- assuming provider timestamps are already in the expected zone
- mixing publication date with ingestion time
- after-hours misclassification
- non-trading-day mapping errors

10.7 Feature redundancy
- returns, log returns, momentum, slope, RSI-like indicators, and derivative-like transforms can encode overlapping information
- without disciplined ablations the project can confuse redundancy with innovation

10.8 More-data-versus-more-signal confusion
- adding more news sources does not guarantee stronger predictive content
- adding a KB branch does not guarantee better generalization
- adding more horizons does not guarantee deeper understanding
- adding more features can simply increase research degrees of freedom

10.9 Modularity that harms comparability
- if every new branch quietly changes upstream data selection or target construction, modularity becomes a source of benchmark drift rather than benchmark cleanliness

10.10 Architecture complexity masking weak labels
- complex multimodal systems can look impressive while actually depending on weak or noisy targets
- in this project, the core risk is not lack of architecture but overbuilding before the target and evaluation family are frozen

10.11 Pilot-illusion risk
- smoke artifacts prove the plumbing exists
- they do not prove the thesis hypothesis is empirically supported

10.12 Provider-confidence illusion
- documented endpoints and pricing do not by themselves prove useful historical coverage for the exact research window and tickers
- live manual verification remains required

SECTION 13. DEEP INVESTIGATION OF DERIVATIVE-BASED FEATURE IDEAS

SUBSECTION 13.1. Clarifying what derivative could mean here

The derivative idea is not one idea. It is at least several distinct technical families.

Discrete first differences
- Example: close_t - close_t-1
- Main issue: scale-dependent and less comparable across stocks than normalized returns

Percentage changes
- Example: close_t / close_t-k - 1
- Usually a more defensible version of “first derivative” in finance

Log returns
- Example: log(close_t) - log(close_t-k)
- Usually nearly the same family as percentage change at daily scales, but often better behaved analytically

Rolling slopes
- Example: slope of log close or cumulative return over a rolling window
- Often a stronger, more interpretable “derivative-like” representation than raw differences

Local trend estimates
- Smoothed moving-window slope, possibly over transformed price or benchmark-relative residual series

Second differences
- Example: x_t - 2x_t-1 + x_t-2
- Potentially interpretable as acceleration or curvature, but very noise-sensitive

Curvature-like transforms
- Change in slope across windows or second derivative after smoothing
- Can sound elegant but are often fragile and hard to distinguish from noise

Derivatives on smoothed series
- Compute first or second changes after smoothing returns, prices, or volatility
- More defensible than raw second differences, but still requires tight benchmarking discipline

Derivatives on transformed OHLCV instead of raw OHLCV
- derivatives of log close
- derivatives of volatility proxies
- derivatives of volume surprise
- derivatives of benchmark-relative return series

This distinction is essential. If “derivative” really means normalized change or rolling slope, then the proposal is not radically new. If it means raw second difference on raw OHLCV, then it is novel mostly in the weak sense that many fragile transforms can be invented.

SUBSECTION 13.3. Comparison against stronger alternatives

Simple returns
- Stronger because they are the canonical normalized first-change family already used widely and easy to interpret.
- Derivative-like raw first differences should be judged against simple returns first, and they will usually lose.

Log returns
- Stronger because they retain the useful part of continuous-change logic without inventing new fragility.
- Any “derivative” on price levels should be compared against log returns before being considered novel.

Momentum
- Stronger because it directly captures persistent trend over windows like 5d, 10d, 20d.
- Many rolling derivative or slope ideas are simply momentum with new naming.

Rolling volatility
- Stronger because it captures risk-state information robustly and often matters more for return predictability than higher-order price curvature.

Range-based measures
- Stronger because OHLC range uses more of the daily bar than close-only transforms and has clear literature support [P30] [P31] [P32].

Shock indicators
- Stronger because they directly encode unusual return, volatility, or volume events instead of inventing smooth curvature language for what is effectively a shock.

Trend or slope features
- Stronger because slope on transformed series is usually the cleanest derivative-like family and already widely interpretable.

Reversal features
- Stronger because many second-order ideas are really just noisy proxies for mean reversion.

Volume-price interactions
- Stronger because they directly encode the market-attention and liquidity dimensions that often mediate the response to news.

Smoothed curvature proxies
- These are the closest “honest” derivative competitors because they at least acknowledge the need to smooth before taking second-order changes.
- Even so, they should still remain extension-only unless proven otherwise.

Factor-neutral residuals
- Stronger because they align directly with the thesis question of incremental value beyond common factors, which is more relevant than mathematically rich market transforms.

Regime features
- Stronger because they explain when the same event-state may or may not matter, which is often more valuable than adding higher-order local motion transforms.

SUBSECTION 13.4. Hard critique

Strongest argument in favor
- A narrow family of normalized first-order motion or slope-like features could capture short-to-medium changes in local market motion that interact with event-state information, especially on 5-day and 20-day horizons.

Strongest argument against
- Most derivative-like content of real value is already captured by stronger and more standard families such as returns, momentum, range-based volatility, and volume surprise. What remains is often scale-dependent noise, redundancy, or search-space inflation.

Best narrow case where derivatives are worth testing
- A late-stage appendix experiment using a very small, predeclared family of normalized first-order transforms or slopes on transformed series, compared directly against standard momentum/range/liquidity families under a frozen benchmark family.

Best case where they are a distraction
- Early in the restart, before the main market-only versus event-state benchmark is stable, or when they are expanded into many windows and many transform definitions without strong prior justification.

Should the derivative proposal be core, strong extension, optional experiment, or probably rejected?
- Core: no
- Strong extension: only for a narrow first-order transformed family if later evidence is supportive
- Optional experiment: yes, definitely
- Probably rejected: broad second-order raw-derivative families and uncontrolled window grids are close to this status already

SECTION 16. METHODOLOGY FAMILIES AND IMPLEMENTATION FAMILIES

This section focuses on cross-cutting implementation choices rather than the broader family map above.

16.1 Symbolic event-state versus embedding-based event-state

Symbolic event-state
- Conceptual logic: summarize news through event categories, tags, or sentiment-like symbolic features.
- Common implementations: event lexicons, event classifiers, counts, entity-event tags.
- Strengths: interpretable, cheap, easy ablation.
- Weaknesses: misses semantic nuance, brittle labeling.
- Likely repo fit: moderate to high as an extension branch.
- Benchmark burden: low.
- Interpretability: high.

Embedding-based event-state
- Conceptual logic: represent recent news with dense semantic vectors pooled over time.
- Common implementations: frozen dense embeddings, finance-domain encoder embeddings, pooled article vectors.
- Strengths: strong semantic capacity, reproducible if frozen, already repo-compatible.
- Weaknesses: less directly interpretable.
- Likely repo fit: very high.
- Benchmark burden: low to medium.
- Interpretability: medium.

16.2 Early fusion versus intermediate fusion versus late fusion

Early fusion
- Conceptual logic: combine features immediately.
- Strengths: simple.
- Weaknesses: weak for asynchronous modalities.
- Repo fit: high technically.
- Benchmark burden: low.
- Interpretability: medium.

Intermediate fusion
- Conceptual logic: encode each modality somewhat, then interact.
- Strengths: better cross-modal flexibility.
- Weaknesses: more tuning burden.
- Repo fit: moderate.
- Benchmark burden: medium.
- Interpretability: medium to low.

Late fusion
- Conceptual logic: keep modalities separate as long as possible.
- Strengths: clean ablations, strong modularity, easy missing-modality handling.
- Weaknesses: may miss some interactions.
- Repo fit: very high.
- Benchmark burden: low.
- Interpretability: high.

16.3 Shared-encoder versus branch-based fusion

Shared-encoder design
- Logic: use one shared representation backbone across modalities or horizons.
- Strengths: parameter sharing, possibly better efficiency.
- Weaknesses: can blur modality-specific reasoning.
- Repo fit: moderate.
- Benchmark burden: medium.
- Interpretability: lower.

Branch-based design
- Logic: use separate branches for market, event-state, and maybe static context.
- Strengths: modular, ablation-friendly, naturally aligned with repo structure.
- Weaknesses: can underuse cross-modal synergies if fusion is too naive.
- Repo fit: very high.
- Benchmark burden: low.
- Interpretability: high.

16.4 Ranking-first versus regression-first versus risk-first formulations

Regression-first
- Logic: preserve numeric excess-return target as main thesis framing.
- Strengths: closest to current project identity.
- Weaknesses: point-fit may look weaker than actual ranking usefulness.
- Repo fit: high.
- Benchmark burden: low.
- Interpretability: high.

Ranking-first
- Logic: prioritize relative ordering across stocks.
- Strengths: often more financially meaningful.
- Weaknesses: changes the primary problem framing.
- Repo fit: moderate.
- Benchmark burden: medium.
- Interpretability: medium.

Risk-first
- Logic: prioritize downside or uncertainty prediction.
- Strengths: richer risk-aware thesis angle.
- Weaknesses: secondary to current core question.
- Repo fit: moderate.
- Benchmark burden: medium to high.
- Interpretability: medium to high.

16.5 Market-neutral targets versus raw targets

Raw targets
- Strengths: simple and baseline-friendly.
- Weaknesses: confound market direction with stock-specific signal.
- Repo fit: already supported.

Market-neutral or factor-neutral targets
- Strengths: better match to “incremental information” question.
- Weaknesses: extra assumptions and benchmark/factor dependencies.
- Repo fit: moderate, because excess-return logic is already present but full factor-neutralization is not core yet.

16.6 Static company context versus dynamic context

Static context
- Strengths: low leakage, easy to integrate, interpretable.
- Weaknesses: limited novelty.
- Repo fit: high.

Dynamic context
- Strengths: potentially richer and more timely.
- Weaknesses: high leakage risk and timing burden.
- Repo fit: lower.

16.7 Modular branch design versus tightly coupled design

Modular branch design
- Strengths: branch separability, clean ablations, preserved comparability.
- Weaknesses: can miss some interactions.
- Repo fit: excellent.

Tightly coupled design
- Strengths: potentially more expressive.
- Weaknesses: high attribution difficulty and benchmark burden.
- Repo fit: weaker under current maturity.

16.8 Expert-routed versus non-expert modularity

Non-expert modularity
- Strengths: clearer and easier to benchmark.
- Weaknesses: less adaptive.
- Repo fit: excellent.

Expert-routed modularity
- Strengths: may model conditional signal structure.
- Weaknesses: harder to justify, benchmark, and debug.
- Repo fit: low to moderate for now.

16.9 Deterministic outputs versus uncertainty-aware outputs

Deterministic outputs
- Strengths: simpler, easier to compare, current repo-aligned.
- Weaknesses: less scientifically rich about uncertainty.
- Repo fit: high.

Uncertainty-aware outputs
- Strengths: stronger risk narrative and proper scoring possibilities.
- Weaknesses: extra evaluation and calibration burden.
- Repo fit: moderate as a later extension.

SECTION 21. FINAL RESEARCH-STATE CONCLUSION WITHOUT FINAL SELECTION

1. What the project should now be about at its core

It should now be about a disciplined test of whether a leakage-safe, aligned, temporally aggregated event-state representation of recent company news adds value beyond conservative market-only baselines for end-of-day multi-horizon excess-return forecasting.

2. Whether the derivative idea appears worth serious attention

It appears worth serious attention only as a later, narrow, explicitly comparative feature-family experiment. It does not appear strong enough to define the restart. First-order normalized or slope-like versions are the only clearly defensible starting point. Broad second-order or curvature-style expansions look much weaker and more benchmark-dangerous.

3. What the strongest unresolved theoretical questions are

- Does the market-only branch show stable out-of-sample learnability under the final serious benchmark family?
- Does the event-state branch add robust, conditional, or negligible value beyond that market baseline?
- Which event-state design choices matter most: lookback, decay, semantics, or scalar enrichment?
- Are the strongest gains regression-like, ranking-like, or only conditionally present in high-information settings?
- Does any derivative-like family survive fair comparison against stronger standard alternatives?

4. What the most dangerous next mistakes would be

- benchmark drift hidden under the language of “same experiment”
- architecture inflation before the core question is settled
- overclaiming small or unstable gains
- treating pilot-scale artifacts as empirical proof
- skipping manual provider verification
- using attractive extensions to avoid resolving the core market-only versus event-state question

5. What should definitely not be done next

- do not make derivative-family expansion the next main research axis
- do not add end-to-end text fine-tuning now
- do not add time-varying company profile branches now
- do not jump to graph or MoE cores now
- do not let a target-zoo replace one frozen serious target family
- do not use a giant live universe as the first serious thesis benchmark

6. What should be stabilized before any new implementation starts

- one frozen serious universe file
- one frozen split-source and adjusted-price policy
- one frozen benchmark series
- one frozen text variant
- one frozen event-state default
- one frozen target family
- one frozen fold protocol
- one reproducible reporting packet
- one verified provider-reality checklist

7. What parts of the state of the art appear most relevant to event-state forecasting

- event abstraction and event representation literature
- finance-domain text encoders rather than generic sentiment-only pipelines
- late and gated multimodal fusion families
- multi-horizon architectures with explicit horizon outputs
- ranking evaluation as a serious secondary benchmark family
- purge and embargo temporal evaluation
- factor-neutral or excess-return framing
- conditional heterogeneity analysis across news density and time periods

8. What parts of the prior project history should be preserved versus discarded

Preserve:
- the move away from price-level prediction
- the event-state concept
- the split-safe label discipline
- the as-of-close alignment logic
- the baseline-first philosophy
- the saved-artifact and manifest architecture

Discard or demote:
- any tendency to let architecture novelty become the thesis before the core question is answered
- any temptation to preserve derivative elegance as if it were automatically signal
- any scope-expansion impulse that blurs the central market-only versus event-state comparison
- any willingness to treat smoke outputs or pilot validations as final evidence

Final nonfinal conclusion

This restart should produce a broader and more explicit map of the research space than earlier investigations, but it should also impose stricter discipline on what counts as core truth. The most important outcome of this investigation is not a selected architecture. It is a stronger boundary around the real question.

The project now has enough theory, enough implementation substrate, and enough warning signs to stop acting like an exploratory pile of good ideas and start acting like a controlled scientific program.

The right operating rule remains simple:

freeze first, verify second, benchmark third, interpret fourth, extend last.
