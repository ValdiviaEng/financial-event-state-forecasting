EXECUTION PLAN
Project: event-state-forecasting

Purpose
- This file is the build-order roadmap for the entire repository.
- It defines the recommended order in which every file should be implemented, hardened, revisited, tested, and documented.
- It is intentionally detailed and workflow-oriented rather than brief.

Progress snapshot
- Stages 0 through 14 are now implemented in first-pass form.
- Stage 15 documentation hardening is now complete in first-pass form.
- The plan remains useful as a maintenance and extension guide, but it is no longer only prospective.

Important constraints
- This plan assumes the local `.env` file exists and remains private.
- This plan uses the current `README.md` as the project-level source of truth for research framing, risk priorities, and architectural decisions.
- This plan uses `Complete_guidebook.txt` as the file-by-file repository map.

Primary references to keep open while executing this roadmap
- `README.md` - the main research and engineering specification.
- `Complete_guidebook.txt` - the file-by-file map and current state summary.
- `docs/architecture_overview.md` - intended system structure.
- `docs/data_layout.md` - intended dataset layering.
- `docs/evaluation_protocol.md` - intended evaluation rigor.
- `docs/implementation_roadmap.md` - existing short roadmap that this file expands.

How to read this plan
- Each stage has a clear goal, dependencies, files to implement or update, tests to run, common traps, and revisit conditions.
- "Implement" means writing executable logic.
- "Update" means keeping documentation/config/support files aligned with the now-real behavior.
- "Revisit" means the file may be logically correct at first pass but must be reopened once downstream modules reveal missing requirements.

Non-negotiable execution principles
- Correctness before speed.
- Reproducibility before convenience.
- Leakage safety before model sophistication.
- Split-handling before labels.
- Frozen intermediate artifacts before training.
- Baselines before multimodal complexity.
- Do not widen scope until the previous stage has both code and tests.

README citation policy for this plan
- When a stage is justified by research framing or risk, this plan cites the relevant `README.md` section by name.
- Use those sections as the authoritative rationale when questions arise during implementation.

STAGE 0 - BOOTSTRAP, TOOLING, AND REPOSITORY HYGIENE
================================================================================

Goal
- Ensure the repository can be installed, imported, linted, and tested before deeper logic is added.

Reference sections in `README.md`
- `Installation`
- `Software Engineering Plan`
- `Current Implemented Components`

Files in scope
- `.env.example`
- `.gitignore`
- `requirements.txt`
- `pyproject.toml`
- `Makefile`
- `LICENSE`
- `src/__init__.py`
- `src/utils/__init__.py`
- `src/cli/__init__.py`
- `src/data/__init__.py`
- `src/features/__init__.py`
- `src/models/__init__.py`
- `src/split/__init__.py`
- `tests/__init__.py`

Execution order inside Stage 0

0.1 - Freeze environment interface
- Confirm `.env.example` still matches real runtime needs.
- Revisit `.env.example` only if a new required runtime variable appears in code.
- Do not read or print `.env` itself.

0.2 - Freeze dependency surface
- Keep `requirements.txt` and `pyproject.toml` synchronized.
- Add new dependencies only when a file actually uses them.
- If a module imports a package not yet installed, update both files immediately.

0.3 - Keep tooling safe
- Ensure `.gitignore` excludes all generated raw/interim/final data and private `.env`.
- Ensure `Makefile` stays minimal and accurate.
- Do not add fake commands for unimplemented pipelines.

0.4 - Package markers
- Keep all `__init__.py` files lightweight and side-effect free.
- No environment loading, network calls, or eager imports in package markers.

Stage 0 exit criteria
- All imports for implemented modules succeed in a properly installed environment.
- `python -m compileall src` passes.
- `ruff check src tests` passes after installation.
- `pytest` should at least discover the blueprint tests without import failures.

Tests to run after Stage 0
- `python -m compileall src`
- `python -c "import src, src.utils, src.data, src.features, src.models, src.split"`
- `ruff check src tests`

Common traps in Stage 0
- Adding imports to blueprint files without adding dependencies.
- Letting `.env.example` drift away from real code requirements.
- Hiding build logic in package markers.

Revisit conditions
- Reopen this stage whenever any new top-level dependency, CLI command, or output directory is introduced.

================================================================================
COMMON DEVELOPMENT TRAPS THAT REQUIRE EXTRA TESTING
================================================================================

Trap 1 - Dot ticker breakage
- Test `BRK.B` and `BF.B` anywhere symbols are normalized, stored, requested, or joined.

Trap 2 - Silent raw/interim/final schema drift
- Add contract tests early.

Trap 3 - Date-order assumptions
- Test ascending and descending provider responses.

Trap 4 - Rate-limit retry logic that duplicates data
- Verify idempotence after forced retries.

Trap 5 - Split-factor direction mistakes
- Always unit-test known split windows.

Trap 6 - After-hours article leakage
- Test before/after market close on normal days and near holidays.

Trap 7 - Summary text inconsistency in embedding cache
- Hash exactly the text actually embedded.

Trap 8 - Hidden train/test normalization leakage
- Make scaler fit location testable and explicit.

Trap 9 - Purge logic detached from actual horizon definitions
- Derive purge windows from `configs/labels.yaml`, not ad hoc constants.

Trap 10 - Baseline vs multimodal non-comparability
- Same data version, same filters, same folds, same metrics.

Trap 11 - Ranking metric misuse
- Compute per-date cross-sectional metrics, not one global rank correlation.

Trap 12 - Overbuilding too early
- Do not add time-varying company profiles, attention pooling, or end-to-end text fine-tuning before the baseline pipeline is stable.
